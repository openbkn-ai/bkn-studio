# Internationalization

BKN Studio uses `i18next` and `react-i18next` for product copy. New user-facing UI text should be added to locale resources instead of being embedded directly in components.

## Locale Resolution

The frontend resolves the active locale in this order:

1. Runtime input injected by the host deployment.
2. Persisted user preference, once a language switcher is introduced.
3. Browser language, normalized to a supported locale.
4. Deployment default locale.
5. `en-US` fallback.

The initial supported locales are `zh-CN` and `en-US`. Regional variants are normalized to the closest supported locale, such as `en-GB` to `en-US`.

## Adding Translation Keys

- Put shared labels in `src/app/locales/resources/common`.
- Put module-specific labels in the owning module's `locales` directory.
- Add the same key to both `zh-CN` and `en-US`.
- Prefer interpolation over string concatenation, for example `t("common.total", { total })`.
- Do not translate user-created data such as object names, prompts, imported schemas, or descriptions.

## Formatting

Use shared helpers from `src/framework/i18n/format.ts` for dates, times, numbers, percentages, and file sizes. Avoid fixed locale literals such as `Intl.DateTimeFormat("zh-CN")` in user-facing code.

## Checks

Run the focused checks while working on internationalization:

```bash
pnpm exec vitest --run src/app/locales/locale-parity.test.ts src/framework/i18n
node scripts/scan-hardcoded-zh.mjs
```

The hardcoded Chinese scanner is currently a report tool. Use `--fail-on-found` when tightening enforcement for a cleaned-up slice.
